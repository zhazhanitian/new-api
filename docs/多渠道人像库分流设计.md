# 多渠道人像库分流设计

## 一、要解决的问题

人像素材的 `asset_id` 只在创建它的火山账号、项目里有效。

以前全进程共用一套 `VOLC_PORTRAIT_*`。再接第二条 Seedance 渠道时，素材建在火山官方账号，另一条渠道的视频模型用不了。

如果按渠道把素材绑死，调用方就得记住「这个素材属于哪个渠道」。同一个素材能在 Seedance 2.0 用、换 Seedance 2.0 Fast 就不能用，对下游产品不可接受。

所以对外只有一个逻辑素材。平台在每个参与渠道的人像库账号里各建一份，生视频时再换成该渠道账号里的上游 ID。

## 二、两条凭据，不要混

1. 人像库：IAM AK/SK + project + region，签到 `open.volcengineapi.com`。
2. 生视频：渠道上的 Ark API Key，请求头 `Authorization: Bearer`。

密钥不写进渠道配置，也不复用渠道 Key。人像库密钥继续放本机环境变量。

## 三、用什么区分渠道

调用方不传渠道。创建素材组和素材时，对 `PORTRAIT_FANOUT_CHANNELS` 里的每个账号各建一份。不配置时只有 `volc`。`volc` 始终存在且排第一，是主账号。

对外的 `group_id`、`asset_id` 取主账号的上游 ID。同一个 ID 可以用于任意 Seedance 模型，包括带渠道尾缀的模型。代码不从模型名解析尾缀。

渠道类型到人像库账号的对应是固定的，不放进渠道配置：

- 中纪视频渠道类型 61：`zj`
- 其他视频渠道：`volc`

同一套人像库密钥给该账号下的各 Seedance 型号共用。创建素材组不传模型 ID。带不带尾缀，上游都是官方满血模型。尾缀只区分渠道账号。

选渠道仍按模型 ID。请求里有 `asset://` 也不会把任务锁到某条渠道。

## 四、凭据怎么取

`volc`：读现有 `VOLC_PORTRAIT_*`。这套可以被系统设置运行时覆盖。

其他标识：进程启动时从 `PORTRAIT_<ALIAS>_*` 读入。

```text
PORTRAIT_ZJ_ACCESS_KEY_ID
PORTRAIT_ZJ_SECRET_ACCESS_KEY
PORTRAIT_ZJ_PROJECT_NAME
PORTRAIT_ZJ_REGION
```

`REGION` 可空，默认 `cn-beijing`。环境变量名里的下划线同时登记成连字符，`byte_plus` 和 `byte-plus` 是同一套。`PORTRAIT_VOLC_*` 故意忽略，避免盖住可热更新的 `VOLC_PORTRAIT_*`。

标识格式：小写字母、数字、下划线、连字符，最长 32。传入的大写会转成小写。未知、非法、或缺少 AK/SK：直接报错，不回落到火山。

非 `volc` 的密钥在包初始化时从进程环境变量读一次。只写进 `.env`、进程启动前没有导出，就读不到。改完需要重启。`dev.sh` 启动前会导出 `VOLC_PORTRAIT_*` 和 `PORTRAIT_*`。`PORTRAIT_FANOUT_CHANNELS` 同样在启动时读取。

## 五、数据怎么记

`portrait_groups`、`portrait_assets` 不再有 `portrait_channel` 列。渠道信息只在绑定表。

`portrait_group_bindings`：逻辑 `group_id`、渠道标识、该渠道的上游素材组 ID。唯一键是（`group_id`，渠道）。

`portrait_asset_bindings`：逻辑 `asset_id`、渠道标识、该渠道的上游素材 ID、状态、`resolved_url`、`last_error`。唯一键是（`asset_id`，渠道）。

逻辑 ID 就是主账号（`volc`）的上游 ID。线上已有素材的 `remote_*_id` 继续有效，不迁移。

`portrait_assets.status` 是汇总结果：任一渠道 `Failed` 则 `Failed`；全部 `Active` 才 `Active`；全部还是 `Submitted` 则 `Submitted`；否则 `Processing`。`resolved_url` 优先取主账号的。

没有绑定记录的线上历史素材视为只在火山：状态仍用原来的 `status`，查询和轮询按 `volc` 凭据。

创建素材不接收渠道。先保证所属素材组在每个参与渠道都有组绑定，缺的当场补建，再在每个渠道创建素材。本地找不到这个素材组时直接报错。

轮询扫非终态绑定，按每条绑定自己的标识取凭据，同一标识在一轮里缓存。解析失败只记日志并跳过，不拖垮其他素材。刷新后重算对应逻辑素材的汇总状态。

响应里的 `channels` 列出每个渠道的 `portrait_channel`、`status`、`last_error`。审核失败时调用方直接看到是哪个渠道、上游返回了什么。

## 六、生视频怎么走

选渠道仍按模型 ID，不因为请求里有 `asset://` 就锁到某条渠道。

不同渠道用不同的对外模型 ID。同一模型 ID 挂多条渠道不在这次范围内。

渠道上的模型重定向把对外 ID 转成上游官方 ID，例如 `doubao-seedance-2-0-fast-zj` 转到 `doubao-seedance-2-0-fast-260128`。请求体里的 `model` 用上游官方 ID。

中纪是独立渠道类型 61（中纪视频），不挂在火山渠道类型下面。

视频适配器复用火山的请求体和计费，只改两处：

- 提交和查询路径是 `{base}/v1/contents/generations/tasks`，不是火山的 `/api/v3/...`。
- 状态词 `in_progress` 看成 `processing`，`completed` 看成 `succeeded`。`queued`、`succeeded`、`failed` 保持原样。

因为适配器是嵌入火山适配器的，`DoRequest` 必须由中纪自己实现。否则接收者会变回火山类型，URL 仍拼成 `/api/v3`。

服务日志里 `BuildRequestBody` 打出来的 submit request 仍可能显示 `/api/v3`，那一行不是实际发出的地址。`asset://` 的改写发生在打这行日志之前，日志里的素材 ID 已经是当前渠道的上游 ID。

提交前，按当前渠道类型得到人像库标识，把 `image_url`、`video_url`、`audio_url` 里的 `asset://逻辑ID` 改成 `asset://该渠道上游ID`。只检查当前选中渠道的那条绑定：

- 素材必须属于当前用户。
- 该渠道绑定必须是 `Active`，否则返回 400，带上 `last_error`，不发给上游。
- 渠道是 `volc`、且这条素材没有任何绑定（线上历史素材）：要求本地记录存在且 `status` 为 `Active`，然后原样使用逻辑 ID。火山生视频不看中纪补建进度。

`BuildRequestBody` 每次尝试都从原始请求重新生成，渠道重试换到另一条渠道时会按新渠道重新改写。

## 七、计费和广场展示

计费系数表的键是官方模型 ID。

对外 ID 自己就在表里时，直接用对外 ID，不看映射，避免改动现有火山结算。

对外 ID 不在表里、且渠道映射指向一个在表里的官方 ID 时，系数回退到这个官方 ID。

没有映射的改名拿不到系数。

广场分档展示单独跟着启用渠道的 `model_mapping` 找到官方 ID 的分档。`price_tiers` 只给展示，不进结算。

后台仍要给对外模型 ID 配价格。日志里可能出现 `model price not found:` 带尾缀的模型名，随后仍按映射后的官方系数扣费。

人像素材改写发生在预扣费之后，不参与系数计算。

## 八、一条请求的实际顺序

1. 创建素材组。平台在每个参与渠道各建一个组，返回主账号的 `group_id`。
2. 用这个 `group_id` 创建图片或视频素材。每个渠道各注册一份，素材 ID 取主账号的上游 ID。素材组若还缺某个渠道的组，先补建再创建素材。
3. 查询到汇总 `status=Active`。这时每个渠道的绑定都是 `Active`。任一渠道失败则整条素材是 `Failed`，`channels` 里有该渠道的 `last_error`。
4. 用 `asset://{asset_id}` 调 `POST /v1/video/generations`。`model` 用要调用的对外模型 ID，火山模型和带尾缀的模型都可以用同一个素材 ID。
5. 平台按模型选到对应渠道，把 `model` 重写成官方 ID，把 `asset://` 改写成该渠道账号里的上游素材 ID，发到该渠道的视频地址。

## 九、明确不做的事

不把 AK/SK 配到渠道上。

不按模型 ID 选人像库账号，也不从模型名解析尾缀。

不因为请求里有 `asset://` 就把任务锁到某条渠道。选渠道仍然只看模型 ID。

生视频时会改写 `asset://`，并只校验当前选中渠道的绑定。不要求一次请求里的素材在其他渠道上也同时再验一遍：汇总状态已经保证，对外 `Active` 时每个参与渠道都是 `Active`。

不改现有火山模型使用线上历史素材的行为。没有绑定、且本地状态为 `Active` 的素材，火山渠道原样放行。

上游没有删除素材接口。某个渠道创建失败时，整体返回错误，已建成的上游素材不清理。

## 十、线上历史数据

线上已有素材全在火山账号，没有绑定记录。

- 逻辑 ID 就是原来的火山 ID，调用方手里的 `group_id`、`asset_id` 继续有效。
- 没有绑定的素材，火山模型照常使用。中纪模型会返回「尚未在渠道 zj 就绪」，直到补建完成且该渠道审核通过。
- 补建是 `POST /api/portrait/backfill`，需要 Root 登录态。它把缺少渠道绑定的素材，用已保存的 `source_url` 补到每个参与渠道。已补过的跳过，审核失败的历史素材不补。可以重复执行。
- 往历史素材组里新加素材时，缺的渠道素材组会当场补建，不依赖这次补建任务。

上线顺序：

1. 发布新代码，`PORTRAIT_FANOUT_CHANNELS` 保持默认（只有 `volc`）。
2. 配好 `PORTRAIT_ZJ_*`，执行一次补建。
3. 把 `PORTRAIT_FANOUT_CHANNELS` 改为 `volc,zj` 并重启，同时开放中纪渠道。
4. 再执行一次补建，补上第 2 步到第 3 步之间新建的素材。
